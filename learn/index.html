Pi Agent：从提问到工具结果

阅读版基于原始 Markdown 整理；内容先于测试，测试先于答案。

学习目标：能解释“帮我看一下桌面上有哪些文件”从用户输入，到模型调用工具，再到最终回答的完整闭环。

1. 先建立一个正确认识

Pi 不会自行理解中文，也不会自动执行 ls。Pi 是 Agent Harness / Runtime：大模型负责理解和决策；Pi 负责组织上下文、调度工具、保存会话，并展示过程。

模型负责想；工具负责连接真实世界；Harness/Runtime 负责让整个循环可靠、可控、可追踪。

2. 一次请求的完整链路

你：“帮我看一下桌面上有哪些文件”
  → Pi TUI 接收输入
  → AgentSession 组装规则、历史与工具 Schema
  → LLM 判断需要观察真实环境
  → Tool Call：请求 bash / find / read
  → Tool Runtime 调度工具
  → Shell / 文件系统返回 stdout、stderr 或错误
  → Tool Result 进入 Session 并回到模型上下文
  → LLM 基于真实结果生成最终回答

有工具的任务通常至少需要两次模型请求：第一次决定调用工具；第二次读取 Tool Result 并组织自然语言答案。

3. 谁在思考？谁在行动？

组件职责
Pi TUI接收输入、展示消息和工具过程；不决定命令。
AgentSession管理会话、队列、工具、持久化、压缩和重试。
LLM理解意图、选择工具、阅读结果、生成回答。
Tool Runtime找到工具实现、传入参数与 AbortSignal、包装结果。
Shell / 文件系统执行真实操作；不知道模型意图和上下文。
Session JSONL保存可恢复、可回放、可审计的运行轨迹。

4. Tool Call：模型提出行动请求

模型不直接触碰桌面文件。它根据 Pi 暴露的 Tool Schema 输出结构化意图，例如：

{
  "id": "call_01",
  "name": "bash",
  "arguments": { "command": "find ~/Desktop -maxdepth 1 -type f" }
}

Tool Schema 是模型可见的契约，包含名称、描述和参数结构；它不等于真正执行命令的代码。

5. Tool Result：Runtime 返回外部事实

Pi 找到 bash 工具，执行受控 Shell 命令，收集 stdout/stderr 和退出状态后，生成与调用 ID 对应的结果：

{
  "toolCallId": "call_01",
  "toolName": "bash",
  "isError": false,
  "content": [{ "type": "text", "text": "...desktop files..." }]
}

Tool Result 是 Agent 的“感官输入”：模型通过它观察文件、测试、网页、数据库或 API，而不是直接获得操作系统权限。

6. 为什么 Session 很重要？

Pi 默认将会话保存为 JSONL。用户消息、助手消息、Tool Call、Tool Result、模型配置和压缩摘要共同构成轨迹。这支持恢复、分支、导出、回放与审计。

Session 不只是最终聊天文本。若丢失工具过程，就很难回答“模型当时看到了什么、为什么这样回答”。

7. 取消、超时与大输出

当用户按 Escape，TUI 发起 abort，Runtime 通过 AbortSignal 传给工具；bash 工具应停止 Shell 及其子进程树。只停止界面而让命令继续运行不是合格的取消。

大输出不能无限进入上下文：工具应流式显示、限制行数和字节数、保存完整输出引用，并让模型用 offset、limit 或更窄查询继续观察。

8. Prompt 不是安全边界

“不要执行危险命令”是模型行为指引，不能替代强制控制。模型可能误解、幻觉或受提示注入影响。安全措施必须位于 Tool/Runtime/OS 层，例如工具白名单、路径校验、最小权限、审批、容器或远程沙箱。

9. 总结

用户意图
→ 模型决定观察方式
→ Runtime 受控执行工具
→ Tool Result 作为事实回到模型
→ 模型给出回答
→ Session 保存完整轨迹
