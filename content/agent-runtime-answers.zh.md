# Agent 底层机制能力测验：参考答案与评分标准

> 请完成试卷后再阅读本文。  
> 总分 100 分；90 分为通过线。安全与工具控制题（17、18、22、23）不应出现根本性误解。

---

# 第一部分：基础判断题（20 分）

每题 2 分：判断正确 1 分；理由完整 1 分。

| 题号 | 答案 | 关键理由 |
|---:|---|---|
| 1 | 错误 | Pi 提供工具和执行环境；模型根据上下文、工具说明和规则决定是否调用 `ls`、`find` 或其他工具。 |
| 2 | 错误 | 模型不直接拥有本机文件系统权限；它只能通过 Pi 可用工具获得经过包装的结果。 |
| 3 | 正确 | 工具执行结果必须作为 Tool Result 回到模型上下文，模型才可以基于真实观察继续推理。 |
| 4 | 正确 | 无工具调用时通常一次请求即可结束；工具任务通常是“决策调用”加“读取结果后回答”，至少两次。 |
| 5 | 正确 | 工具名是抽象接口；Extension 或运行配置可以让 `bash` 对接本地 Shell、容器、SSH 或云端执行器。 |
| 6 | 错误 | Tool Schema 是模型可读的工具契约，模型需要据此理解工具用途和参数；Pi 不会仅凭 Schema 替模型决定调用。 |
| 7 | 正确 | 调用 ID 将 Tool Call 与 Tool Result 关联，确保模型、日志、UI 和 Runtime 都可识别结果归属。 |
| 8 | 错误 | 取消必须传播至真实执行单元；仅停止 TUI 会让后台命令继续运行，造成资源、安全和状态问题。 |
| 9 | 错误 | 工具调用和结果也是运行轨迹；保存它们是恢复、审计、回放和理解模型依据的重要前提。 |
| 10 | 正确 | 三者都属于轨迹，但来源不同：模型内容/调用来自 LLM，Tool Result 来自 Runtime 执行工具后的外部观察。 |

# 第二部分：机制解释题（32 分）

每题 4 分。以下为评分要点；表达方式可以不同。

## 11. 组件边界（4 分）

- 1 分：Pi/TUI 是交互与运行环境，不是推理主体；
- 1 分：LLM 理解请求、规划和发出 Tool Call；
- 1 分：工具是受 Runtime 调度的外部能力；Shell/OS 执行真实系统操作；
- 1 分：模型没有电脑权限，只有“请求调用工具”的能力。

## 12. 模型请求前的上下文组装（4 分）

任意五项，每项合理得分：

```text
- System Prompt；
- AGENTS.md / CLAUDE.md 等上下文规则；
- 已加载 Skill 的内容；
- 当前激活工具的 Schema、描述和参数；
- 当前 Session 分支上的历史消息；
- 过去的 Tool Result；
- 当前用户消息；
- 当前模型、Provider、thinking level 等运行配置；
- 可能的上下文压缩摘要。
```

必须指出：这些信息由 Pi/AgentSession 组织后交给模型，而不是模型自行从磁盘搜集。

## 13. Tool Schema（4 分）

- 1 分：是模型调用工具时可见的结构化契约；
- 1 分：包含工具名、描述、参数及参数类型/可选性，常使用 JSON Schema；
- 1 分：模型根据它生成结构化 Tool Call；
- 1 分：Schema 不等于实现；真正执行由 Pi 注册的工具代码完成。

## 14. Tool Call 与 Tool Result（4 分）

- 1 分：第一个对象是模型发出的调用意图；
- 1 分：第二个对象是工具实际执行后的观察结果；
- 1 分：`call_01` 与 `toolCallId: call_01` 是关联键；
- 1 分：Tool Result 会进入下一轮上下文，且包含成功/失败状态。

## 15. Tool Result 是感官（4 分）

必须说明“模型通过结果文本/结构化内容观察外部世界”，并给出至少三例，例如：

```text
read → 文件、代码或图片内容；
ls/find → 文件系统结构；
grep → 关键词位置；
bash → 测试结果、Git 状态、系统信息；
HTTP 工具 → 外部 API 数据；
数据库工具 → 查询结果；
浏览器工具 → 网页内容。
```

## 16. 大输出处理（4 分）

每点 1 分：

```text
- 大结果消耗上下文窗口与 Token，可能挤掉重要历史；
- 传输/渲染/持久化成本和失败风险上升；
- 用户和模型都难以从噪声中定位重点；
- 应截断、保存完整输出引用、提供 offset/filter/grep 等继续观察手段。
```

## 17. 取消链路（4 分）

- 1 分：TUI 接收 Escape，调用 Session/Agent 的 abort；
- 1 分：Runtime 将取消状态通过 AbortSignal 传给当前工具；
- 1 分：bash/Shell 工具应终止进程及可能的子进程树，并收敛为 aborted 结果；
- 1 分：仅停止 UI 会遗留实际进程，产生资源泄漏、意外副作用和状态不一致。

## 18. 为什么 Prompt 不是安全边界（4 分）

至少三点，四点满分：

```text
- 模型可能误解、幻觉、被提示注入或不遵守指令；
- Prompt 无法在 OS 层阻止一个已经被执行器接受的命令；
- 不同模型、版本、上下文状态下行为不稳定；
- 真正可验证的限制应在 Tool/Runtime 层：allowlist、路径校验、审批、容器、网络隔离、最小权限；
- 安全策略应可审计、可测试、可强制执行。
```

# 第三部分：场景与排障题（32 分）

## 19. 无工具却声称知道桌面内容（8 分）

| 要点 | 分值 |
|---|---:|
| 指出这是无依据回答/幻觉：当前上下文没有事实来源 | 2 |
| 说明应要求或促使模型调用只读目录工具，之后基于 Tool Result 回答 | 2 |
| 可使用 Prompt、工具描述、评测或工作流规则提高“先观察后回答”的可靠性 | 2 |
| 指出 Shell/文件系统并未被调用，因此它们不能“自动修正”模型的虚构回答 | 2 |

加分理解：应避免让模型伪造工具结果；工具结果必须由 Runtime 产生。

## 20. Permission denied（8 分）

满分答案应包括：

```text
1. bash 工具收集 stderr 和非零退出状态；
2. Pi 生成 isError: true 的 Tool Result，并保持调用 ID 对应；
3. Tool Result 进入 Session，也进入下一次模型请求；
4. 模型应如实说明无权限，或在合法情况下询问用户/尝试允许的替代路径；
5. 模型不得凭空声称已列出文件，也不应自行绕过权限边界。
```

每项约 1～2 分。

## 21. 500MB 输出（8 分）

| 要点 | 分值 |
|---|---:|
| 工具可以流式收集 stdout/stderr，并向 TUI 提供部分更新 | 1 |
| 设置字节数与行数上限，不能将 500MB 原样放进模型上下文 | 2 |
| 完整输出应保存到临时/受控文件或可分页的数据源 | 1 |
| Tool Result 中应说明已截断、展示何种片段、给出完整输出位置或后续读取方式 | 2 |
| 模型可使用更窄的命令、offset、limit、grep、指定目录等方式继续获取细节 | 2 |

## 22. 中途补充“只看 PDF”（8 分）

| 要点 | 分值 |
|---|---:|
| B 是默认推荐方式：作为 steering，在当前工具调用结束和下一次模型调用前生效 | 3 |
| A 会丢失已完成结果，且用户并未明确要求停止；仅在用户取消或安全需求下适用 | 1 |
| C 响应过慢，可能让 Agent 继续做不再需要的工作 | 1 |
| steering 进入下一轮模型上下文后，模型可调整为 `-name '*.pdf'` 等更窄查询 | 1 |
| 若用户按 Escape：应 abort 当前 Agent/工具，尝试终止进程树；排队消息可恢复或按产品策略处理 | 2 |

# 第四部分：综合设计题（16 分）

## 23. “只读桌面文件检查 Agent”评分标准

### A. 最小工具集合（3 分）

应仅暴露必要只读能力，例如：

```text
listDesktop({ extension?: string, includeDirectories?: boolean })
readDesktopText({ relativePath: string, offset?: number, limit?: number })
```

也可使用经过严格包装的 `find`/`read`。不应暴露原始任意 `bash`、`write`、`edit`、网络工具。指出“最小权限”得分。

### B. 参数与路径边界（3 分）

必须包含：

```text
- 输入使用相对于 Desktop 的路径，或解析后验证其位于真实 Desktop 根目录内；
- 使用 realpath / canonical path 防御 ../ 路径逃逸；
- 处理符号链接：拒绝跨根链接，或解析后再次验证目标位于根内；
- extension 使用白名单或安全校验，不将用户输入直接拼入 shell 字符串。
```

### C. 只读和安全控制（3 分）

至少包含：

```text
- 不注册 write/edit/rm/mv/network 工具；
- Tool 层进行只读操作与参数验证；
- Runtime/Extension 进行 allowlist、审计和必要审批；
- 不只依赖“请勿修改文件”的 Prompt。
```

### D. Session、异常与内容处理（3 分）

至少包含：

```text
- 记录 user message、tool call、tool result、assistant message；
- 大文件用 offset/limit 与输出上限；
- 二进制文件不按 UTF-8 全量读取，应识别类型或拒绝/给摘要；
- 权限错误以 isError Tool Result 交给模型；
- 记录可用于恢复、审计和回放。
```

### E. 完整循环（4 分）

应明确描述类似链路：

```text
用户：“列出桌面 PDF，再读取说明文件前 100 行”
→ LLM 调用 listDesktop({ extension: "pdf" })
→ Runtime 校验并列出安全根目录下的 PDF
→ ToolResult(pdf 列表)
→ LLM 选择需要读取的文本文件
→ LLM 调用 readDesktopText({ relativePath, limit: 100 })
→ Runtime 再做路径与文件类型校验
→ ToolResult(文本前 100 行)
→ LLM 根据两个真实结果回答
```

若方案允许模型直接运行任意 Shell 或在路径校验失败后仍读取文件，综合题不能超过 8 分。

# 90 分之后还应补齐什么？

通过本测验说明你对基础 Agent Runtime 有较强理解，但市面上的 Agent 应用工程还常要求：

```text
- LLM Provider 差异、流式协议、重试、限流与成本控制；
- RAG、检索质量与上下文策略；
- MCP、OAuth、第三方 API 集成；
- Docker/VM/远程沙箱与密钥管理；
- 多 Agent 编排、任务队列和人工审批；
- Evals、轨迹回放、可观测性与安全测试；
- 产品 UI、权限体验和故障恢复。
```

真正可靠的 Agent 工程师，不只会让工具“跑通”，还要能回答：

> 这次模型到底看到了什么？为何执行这个动作？失败后如何收敛？谁能阻止危险操作？如何复现和审计？
