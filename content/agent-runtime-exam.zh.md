# Agent 底层机制能力测验

> 基于《Pi Agent：从一句话到查看桌面文件的完整工作机制》。  
> **总分：100 分｜建议时长：90 分钟｜通过线：90 分。**  
> 定位：这是 Agent 应用工程的机制理解测验，不是通用编程题，也不是任何公司的正式招聘认证。

## 使用方式

1. 先独立作答，不查看参考答案；
2. 事实题必须说明“谁负责、数据如何流动、失败时如何处理”；
3. 90 分以上才可认为已经具备扎实的 Agent Runtime 基础认知；
4. 即使总分达到 90，**安全与工具控制题（第 17、18、22、23 题）存在根本性误解，也不建议判定为通过**。

# 第一部分：基础判断题（10 题 × 2 分 = 20 分）

每题回答“正确/错误”，并用 **1～2 句话**说明理由。只写正确或错误不得分。

### 1. 
Pi 收到“帮我看一下桌面上有哪些文件”后，会直接把这句话转换为 `ls ~/Desktop` 并执行。

### 2. 
大模型本身有权限读取本机 `/Users/bw/Desktop`，所以工具调用只是为了把结果展示在终端中。

### 3. 
模型调用工具后的结果，需要作为新的上下文再次交给模型；否则模型不知道工具实际观察到了什么。

### 4. 
一个没有工具调用的普通问答，通常只需要一次模型请求；一个“先读目录再总结”的任务通常至少需要两次模型请求。

### 5. 
只要工具调用的名称是 `bash`，模型就一定会访问本机 Shell；同名工具也可能被 Extension 改造成远程执行器或沙箱执行器。

### 6. 
Tool Schema 的主要作用是让 Pi 在运行时自动推断应执行哪个工具，因此模型不需要看到工具描述和参数结构。

### 7. 
工具返回的 `toolCallId` 应与模型发出的工具调用 ID 对应，这样 Runtime 才能把结果关联到正确的调用。

### 8. 
用户按 Escape 后，只需要停止 TUI 的动画；即使后台 Shell 进程继续运行，也不影响 Agent 的取消语义。

### 9. 
Session 持久化的主要价值是保存最终聊天文本，工具调用过程不必保存。

### 10. 
模型输出的文本、Tool Call 和 Tool Result 都属于 Agent 运行轨迹的一部分，但它们在职责和来源上不同。

# 第二部分：机制解释题（8 题 × 4 分 = 32 分）

每题应明确回答：**哪个组件负责、输入是什么、输出是什么、下一步交给谁。**

### 11. Pi、Agent Runtime、LLM、工具、操作系统分别是什么关系？

用自己的话解释这五者的职责边界。重点说明为什么不能把“模型会调用工具”理解为“模型拥有电脑权限”。

### 12. 从用户按下 Enter 到第一次模型请求发出前，Pi 至少需要组装哪些类别的信息？

至少列出 5 类，并说明每类信息的作用。

### 13. 什么是 Tool Schema？

请说明它至少包含哪些信息；它如何帮助模型调用工具；它与工具实现代码之间是什么关系。

### 14. 请说明如下两个对象的区别与联系：

```json
{ "id": "call_01", "name": "bash", "arguments": { "command": "ls ~/Desktop" } }
```

```json
{ "toolCallId": "call_01", "toolName": "bash", "content": [{ "type": "text", "text": "a.txt" }], "isError": false }
```

### 15. 为什么说 Tool Result 是 Agent 的“感官输入”？

请至少举出 3 类不同工具，并说明它们分别让模型观察到什么。

### 16. 为什么 Agent 不应把超大命令输出无条件原样塞进下一次模型请求？

至少从 Token、可靠性、用户体验和后续行动四个角度作答。

### 17. 解释取消（Abort）的完整链路。

从用户按 Escape 开始，说明 TUI、Agent Runtime、AbortSignal、工具、Shell/子进程分别应做什么。再说明“仅停止 UI 显示”为什么不合格。

### 18. 为什么权限控制应位于 Runtime/Tool 层，而不能只依赖 System Prompt 中写一句“不要执行危险命令”？

至少给出 3 个工程原因。

# 第三部分：场景与排障题（4 题 × 8 分 = 32 分）

### 19. 场景：模型没有调用工具，却回答“你的桌面上有 10 个文件”

假设本轮上下文中没有桌面文件列表，也没有先前工具结果。

1. 这是什么问题？
2. 在 Agent 层面，应采取什么修复或防护？
3. 哪个组件**不应该**被误认为可以直接解决这个问题？

### 20. 场景：模型调用了

```json
{ "name": "bash", "arguments": { "command": "find ~/Desktop -maxdepth 1 -type f" } }
```

但工具返回：

```text
find: /Users/bw/Desktop: Permission denied
```

请描述正确的下一轮链路和模型可能采取的合理行为。回答中必须包含 `isError`、Tool Result、后续模型请求三个概念。

### 21. 场景：命令递归扫描了一个巨大的目录，输出了 500MB 内容

请设计从工具执行到模型续推理之间的处理策略。至少覆盖：

- 流式显示；
- 输出上限；
- 完整输出去向；
- 交给模型的摘要/截断信息；
- 模型继续获取细节的方式。

### 22. 场景：工具执行中，用户补充：“只看 PDF，不要看图片。”

请比较以下三种处理方式，并判断推荐方式：

A. 立即强杀当前进程，丢弃一切；  
B. 把补充消息作为 steering，安排在当前工具调用完成后的下一次模型调用前；  
C. 把补充消息当成普通历史文本，等整个任务完全结束后再发送。

说明你的理由；再说明如果用户明确按了 Escape，处理会有什么不同。

# 第四部分：综合设计题（16 分）

### 23. 设计一个“只读桌面文件检查 Agent”

需求：用户可以询问桌面有哪些文件、按扩展名筛选、读取某个文本文件的前 100 行；系统必须禁止修改、删除、移动文件和执行任意网络访问。

请用文字或 ASCII 图设计：

1. 对模型暴露哪些工具；
2. 每个工具允许哪些参数；
3. 如何实现路径边界，防止读取 Desktop 之外的文件；
4. 如何实现只读限制；
5. 如何记录 Session 以便审计和恢复；
6. 如何处理大文件、二进制文件、符号链接和权限错误；
7. 一次“列出 PDF 文件后读取某份文本说明”的完整 Tool Call / Tool Result 循环。

评分重点不是命令写得多，而是边界是否清晰、工具是否最小授权、数据流是否完整。

# 自我评分表

| 分数 | 解释 |
|---:|---|
| 90～100 | 对 Agent Runtime、工具闭环、状态与安全边界理解扎实；具备独立实现或评审基础 Agent 应用的能力。 |
| 80～89 | 已理解主流程，但在会话、错误、取消、权限或工程边界上仍有缺口。 |
| 60～79 | 能描述“模型调用工具”，但尚不足以处理真实生产问题。 |

## 常见失分信号

```text
□ 认为 Pi 自己会理解并决定命令
□ 认为模型可直接读取本机文件
□ 忘记 Tool Result 要再发给模型
□ 只描述成功路径，不描述错误、超时、取消
□ 将 System Prompt 当作唯一安全机制
□ 认为 Session 只保存最终对话文本
□ 忽略 toolCallId 与 toolCall 的关联
□ 把 TUI、Runtime、模型、工具混成同一个组件
```
